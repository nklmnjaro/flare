# FLARE — WORKER EXECUTION POLICY

**Version:** 0.1  
**Status:** Mandatory  
**Owner:** Product Owner / Main Coordinator  
**Date:** 2026-08-06

## Решение по текущему amendment

Ответ аналитика принят как корректный отчёт о предполагаемом закрытии замечаний.

Это не является окончательной приёмкой amended MVP-пакета, пока не переданы и
не проверены:

- обновлённый архив;
- `OWNERSHIP-MATRIX.md`;
- обновлённая acceptance matrix;
- worker-ready задачи `FLARE-001-*`;
- `tools/validate_traceability.py`;
- результаты запуска валидатора;
- detached SHA-256.

Статус:

```text
REVIEW RESPONSE: ACCEPTED
AMENDED PACKAGE: INSUFFICIENT EVIDENCE
IMPLEMENTATION: NOT AUTHORIZED
```

## Правило рабочего времени

Количество часов не является метрикой качества и не заменяет результат.

Однако для первой рабочей волны каждый назначенный воркер должен провести не
менее одного сфокусированного рабочего блока продолжительностью около часа,
если задача действительно требует такого объёма.

Нельзя:

- растягивать простую задачу ради времени;
- писать код до готовности контрактов;
- имитировать занятость;
- считать время доказательством завершения;
- выдавать исследование без решения или артефакта.

Рабочий блок должен закончиться одним из результатов:

```text
READY
BLOCKED
REQUEST CHANGES
TASK ASSUMPTION INVALID
SCOPE CORRECTION REQUIRED
SIMPLER SOLUTION PROPOSED
INSUFFICIENT EVIDENCE
PRODUCT DECISION REQUIRED
DO NOT IMPLEMENT
```

## Обязательный результат каждого воркера

После рабочего блока воркер передаёт:

- короткий статус в чате;
- конкретный результат;
- найденные блокеры;
- выполненные проверки;
- готовый файл или компактный архив;
- SHA-256;
- следующий рекомендуемый шаг.

Сообщение без артефакта допустимо только при доказанном блокере или когда задача
полностью сводится к короткому решению.

## До contract freeze

До принятия `FLARE-000` запрещено начинать production implementation.

Разрешено:

- аналитику — подготовить amended package;
- gatekeeper — проверить amendment и evidence;
- будущим владельцам контрактов — провести критическое review;
- Linter/Quality Tooling — предложить gate matrix без изменения shared files;
- Platform — проверить воспроизводимость предполагаемого bootstrap-подхода без
  создания отдельной архитектуры;
- Backend, Frontend и оба QA — выявить риски, gaps и несовместимые предпосылки.

Запрещено:

- создавать production event models;
- независимо проектировать несовместимые DTO;
- начинать database schema;
- писать UI под неутверждённые статусы;
- фиксировать transport или schema technology без решения `FLARE-000`.

## Главный принцип

Мы покупаем не часы работы.

Мы покупаем проверенный продуктовый результат, снижение риска или доказанный
блокер.
